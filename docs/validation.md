## 计时器修复与回档：2026-11-13

对原版字节码进行只读检查发现：战斗系统生成胜利结果后，界面通过 HUMP timer 的 2 秒回调才设置战斗暂停。原版 timer 使用 `pairs(functions)` 遍历以计时器句柄为键的哈希表；回调可在遍历期间新增计时器，使遍历顺序和本轮实际访问的句柄依赖表布局。

增加诊断后，修复前的密集检查重现了失步：第 26080 帧仍匹配，第 26081 帧最早只出现 `game_paused` 和 `store.paused` 不同，随后产生战斗 tick 和尸体清理差异。诊断的一次正常运行在外层帧 25960 安排胜利回调、26080 执行回调，完成更新后的帧号为 26081。本机诊断证据在 `lab/diagnostic-dense/`，不是新版本通过结果的一部分。

修复只针对 timer 的句柄集合：为注册的句柄分配递增序号，遍历时按该序号生成固定列表，跳过已取消的句柄，回调中新建的句柄留待下一轮。其他表的 `pairs` 保持原行为；原计时器更新函数、浮点算术、回调及战斗代码不变。这里采用了明确的实验调度规则，不能宣称与原版每一种不确定遍历顺序等价。

回档使用全新进程重放而非复制序列化状态。书签保存时间线、目标帧、可观测状态和完整性摘要，载入时先核对运行器／游戏／种子／步长，再重放并比较保存的状态。`--edit` 在比较成功后截断未来输入；任意帧跳转没有保存的对照状态时，报告明确返回 `verified: null`。快照不包含所有内部状态，因此相同快照仍需通过继续运行和独立回放补充验证。

修复版运行器 SHA-256：`ef5bb31a4e2428521f06202746d11986ab30bea480390da623e1fc81be6b351c`。完整首关的 199 条输入及其帧号未修改；更新了样本的运行器哈希，并统一文本换行。新参考运行之后的三次独立回放均严格通过 **232/232** 检查点，包括外层帧 25900–26100 每一帧，第三次改变推进分批并插入真实停顿。三次均为原生胜利、3 星、19 点生命、7 波、金币 42、终点 tick 16290，Lua RNG 调用 3056 次、累计摘要 4097000750。

比较仍包含暂停、tick、尸体、渲染字段和原先失败的终点，没有过滤这些差异。[当前机器可读摘要](southport-normal-validation.json) 对应本机 `lab/verification-timer-fix/` 的完整轨迹。该结果只说明这台机器、这个构建和样本在上述检查范围内通过；不等于所有关卡、所有输入、所有帧或全部隐藏状态均已证明确定。
